# إنشاء حساب ثم تسجيل الدخول ثم الرئيسية

طلب المستخدم: بعد إنشاء الحساب، فتح تسجيل الدخول؛ وبعد نجاح الدخول فتح الصفحة الرئيسية وبدء استخدام الموقع.

## السلوك الجديد

- البريد وكلمة المرور: `/{locale}/signup` ← إدخال البيانات ← `/{locale}/login?next=%2F{locale}&registered=1` ← دخول صحيح ← `/{locale}`.
- Better Auth ينشئ بيانات الحساب دون إنشاء جلسة تلقائية (`autoSignIn: false`). الجلسة تبدأ عند تسجيل الدخول الصحيح فقط، مع بقاء cookies الآمنة وحماية المحاولات كما هما.
- الرابط والرسالة بعد التسجيل لا يحتويان بريدًا أو كلمة مرور، ولا يدّعيان وجود جلسة أو تحقق البريد. صياغة الرسالة محايدة لأن Better Auth يمنع كشف وجود حساب عند إعادة التسجيل ببريد موجود.
- الوجهة الافتراضية للدخول والتسجيل وأزرار بدء المستخدم غير المسجل هي الرئيسية الحقيقية `/ar` أو `/en`، بدل onboarding. بعد الدخول، أزرار العمل تحتفظ بوجهاتها الحالية.
- طلبات `next` الآمنة من الصفحات المحمية، مثل `/ar/account`، تظل محفوظة خلال التسجيل والدخول. الروابط الخارجية والمحارف غير الآمنة وحلقات login/signup تُرفض.
- Google يظل غير متاح دون إعداد مفاتيحه؛ لم يُغيّر هذا العمل قواعد البيانات أو schema أو migrations أو أنظمة المحاسبة.

## التحقق

- `npm run check`: ناجح؛ lint وTypeScript و488 اختبارًا في 61 ملفًا، ثم production build.
- جدول البناء يتضمن الرئيسية وصفحتي login/signup تحت `[locale]` وواجهة `/api/auth/[...all]` العامة.
- اختبارات UI تؤكد التسجيل ثم فتح الدخول، وعدم استدعاء sign-in تلقائيًا، والوجهة الرئيسية في اللغتين، والحفاظ على وجهة صفحة محمية.
- اختبارات المتصفح تستخدم قاعدة localhost منفصلة فقط، دون حذف بيانات أو إرسال حسابات إلى الإنتاج. ينتظر الاختبار حدود حماية الدخول بدل تعطيلها؛ الدليل في `artifacts/auth-signin-home/`.
- فحص المتصفح اكتمل بالعربية والإنجليزية عند 1920 و1440 و1366 و430 و390 بكسل، دون أخطاء متصفح: التسجيل يفتح الدخول بجلسة فارغة، ثم دخول حقيقي يفتح الرئيسية، والخروج ثم إعادة الدخول من سياق موبايل مستقل يعملان مع HttpOnly. SQL أكد بقاء صف مستخدم واحد لكل حساب الاختبار بعد إعادة الدخول.
